# MIRAGE Architecture

## Product operating model\n\nMIRAGE is intended to run continuously as a system-level Linux service. It observes traffic continuously, preserves normal service for legitimate traffic, and selectively steers suspicious traffic to a fabricated deception plane. The enforcement point must be in place before protected services can return application data; a passive detector that reacts only after a real banner or response has escaped is insufficient. All attacker-controlled interactions stay inside isolated sandboxes. A future tray and desktop dashboard are optional management clients and must never be required for runtime operation. See [Runtime and Adaptive Deception Model](runtime-model.md) for the detailed flow and release gates.\n\n## System boundary

MIRAGE is initially a host-level defensive deception system. It discovers protected services, then presents separately configured decoys to untrusted clients. The protected services and decoy execution plane are separate security domains.

Conceptual flow:

1. Untrusted clients connect to host-level network enforcement.
2. Explicitly selected traffic reaches a protocol-aware decoy listener.
3. The listener routes sessions to decoy service implementations.
4. Decoy sessions run in isolated environments.
5. Events flow to telemetry and evidence storage.
6. Protected host services remain on a non-public interface or network.

The implementation must prove this separation with network and filesystem tests before interception is enabled.

## Architectural domains

- **Discovery:** Read-only inventory of listening sockets and service metadata.
- **Policy/configuration:** Validates listeners, decoy profiles, mappings, and operator intent.
- **Protocol compatibility:** Checks that a decoy speaks a protocol appropriate for its exposed port and transport.
- **Interception:** Applies host-level network rules. This layer must fail closed and must not depend on the application remaining healthy.
- **Decoy runtime:** Implements protocol-compatible fake services.
- **Sandbox:** Runs simulated commands or disposable workloads with strict resource and network boundaries.
- **Telemetry:** Captures commands issued within MIRAGE-controlled sessions, protocol events, and session metadata.
- **Intelligence:** Correlates observable indicators across sessions and records confidence and provenance.
- **Evidence:** Stores integrity-protected event records and exportable timelines.
- **Management API/UI:** Allows an authenticated operator to configure and monitor the platform.

## Independent real and decoy identities

A protected-service inventory is used for protection and operator context. It must not dictate the decoy identity.

A mapping binds an externally exposed endpoint to a decoy profile. The decoy may represent a different implementation, version, operating-system narrative, hostname, users, files, and application topology than the real service.

The mapping must not imply that arbitrary protocols are interchangeable. For example, a listener on TCP/443 should normally negotiate TLS and present an HTTPS-compatible application protocol. A fake SSH server on TCP/443 is invalid under the default compatibility policy unless the operator explicitly selects a documented nonstandard-port profile.

## Session consistency

A session should retain a coherent identity. If a session begins with a particular operating-system and service profile, later banners, authentication responses, filesystem contents, and application behaviour should remain consistent with that profile. Dynamic deception may change profiles between sessions or at controlled transitions, not randomly contradict itself mid-session.

## Execution tiers

1. **Protocol simulation:** No general-purpose command execution. Responses are generated by deterministic decoy logic.
2. **Constrained workload:** Real processes may run only inside a separately hardened isolation boundary with no host mounts, no privileged mode, strict syscall policy, resource quotas, and deny-by-default networking.
3. **Disposable VM:** Higher-risk interaction and exploit observation occurs in a disposable VM with snapshots and a separately controlled virtual network.

The first implementation should use protocol simulation only. Stronger execution tiers require dedicated threat-model review and escape testing.

## Failure handling

- Firewall/network enforcement must be independent of the management process.
- A crash, restart, configuration parse error, or telemetry outage must not expose a protected backend.
- Unhealthy decoys should stop accepting new sessions rather than fall through to real services.
- Policy changes should be validated and staged before activation, with rollback support.
\n\n## Always-on operation and selective deception\n\n- The system daemon owns monitoring, policy evaluation, evidence, and sandbox orchestration; it runs independently of any logged-in desktop session.\n- An independently managed enforcement plane controls the path to protected services. Legitimate traffic follows the configured real-service path; traffic selected by policy is redirected to a compatible decoy before protected application data is returned.\n- A decoy identity is fabricated independently of the protected service and remains coherent throughout a session.\n- Decoy workloads have no route to production services, host credentials, or unrestricted host filesystems.\n- The tray and full dashboard are deferred operator clients. Closing them must not stop monitoring or weaken enforcement.\n
